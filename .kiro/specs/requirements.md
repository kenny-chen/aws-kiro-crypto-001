# requirements.md

## 1.0 商业目标︱Business Objective
- 在封闭内测（邀请制）中验证「私密预测对决 + USDC 实际 stake」是否能形成可持续的用户自发邀请与平台抽成收入；在可控风险下于 4 周内产出继续投入或止损的单一商业结论。

---

## 2.0 盈利或价值路径︱Value Creation Path
- 用户创建私密对决并分享邀请链接/二维码 -> 被邀请好友完成钱包连接并用 USDC 入池 -> 对决结算时平台按比例收取手续费（fee%）-> 形成直接收入与可度量的邀请转化漏斗  
- 用户在群聊内重复发起对决（围绕梗、日常争论、热点事件）-> 对决次数/人上升与回访提升 -> 邀请扩散带来新增用户 -> 提升总入池金额与手续费收入

---

## 3.0 关键假设︱Key Assumptions
- 目标用户愿意在“只对好友可见”的场景中完成 WalletConnect 连接并使用 USDC 入池，且入池门槛与体验不会显著抑制转化。  
- 邀请链接/二维码在群聊传播具备足够的转化效率，能让单个发起者带来可观的新增参与者与重复对决次数，从而覆盖获客与运营成本并形成正向收入。

---

## 4.0 成功／失败判据︱Success & Failure Criteria
- 成功：内测期连续 2 周达到「每周完成结算的对决数 ≥ 300」且「平台手续费收入覆盖当周链上/基础设施可变成本并保持正增长」。  
- 失败：内测期连续 2 周「受邀参与者的钱包连接+入池转化率 < 8%」或「结算失败/退款比例 > 2%」导致商业闭环无法稳定成立。

---

## 5.0 退出条件︱Kill Conditions
- 在累计投放/发放 ≥ 1,000 次有效邀请（链接被打开）后仍无法达到「入池转化率 ≥ 8%」或出现可重复的资金安全/结算一致性缺陷（同类缺陷 ≥ 2 次），立即停止新增开发并进入复盘重评。

---

## 6.0 成功／失败判断所需的最小观测视角︱Stakeholder Views on Success / Failure
- 用户视角：我能在 60 秒内完成连接钱包、入池并把私密对决发到群里，且结算结果透明可信。  
- 业务视角：邀请链路能稳定带来新参与者与重复对决，且手续费收入具备可扩张性。  
- 团队视角：资金与结算链路可被审计与监控，线上问题可定位可回滚，且范围不会失控。

---

## 7.0 明确禁止的系统能力︱Negative Capabilities
- 不提供公开大厅或陌生人匹配；不提供公开可搜索的对决列表；默认仅邀请可见。  
- 不提供任何“赔率/隐含概率/实时更优选择”展示；不提供基于入池变化的诱导信息。  
- 不提供订单簿、撮合、交易、二级市场、滑点、做市等交易型能力。  
- 不允许参与者在入池后切换阵营；不允许池子关闭后继续入池。  
- 不提供法币充值/出金、信用卡支付；仅支持 USDC 入池与结算。  
- ~~不提供用户自建市场（MVP 阶段仅 Admin 创建对决主题/问题与结算规则）。~~（v2）  
- 不提供面向公众的市场分发与曝光；用户创建的市场默认仅可生成私密邀请链接传播，且需满足字段与风控约束（见 8.3），不引入“公共可搜索市场库”。（v2）

## 8.0 网站功能承载点︱Business‑to‑Feature Mapping

### 8.1 必需参与角色︱Existence‑Required Roles
- End User（发起/参与私密对决的用户）
- Admin（创建对决主题/规则、执行或确认结算、风控与退款处理；包含对用户创建市场的最小审核/下架能力）（v2）

### 8.2 必需交互视图︱Existence‑Required Views
- 邀请制访问入口（含邀请码或受邀落地页）
- 钱包连接与授权（WalletConnect）
- 对决主题详情与发起对决（选择阵营、stake、池子关闭时间、是否私密、生成邀请链接/二维码）
- 市场创建页（用户创建 market：输入标题、双方选项、结算时间、最小 stake、手续费；默认私密并生成邀请链接/二维码）（v2）
- 受邀加入对决（打开链接/扫码、选择阵营、stake 入池）
- 对战页/对决房间（仅双方/受邀群体可见）：状态、参与者、入池金额、关闭倒计时、实时聊天（不含赔率）（v2）
- 结果公布与结算页（赢家/输家、手续费、可分享结果卡）
- Admin：主题/对决管理、结算操作、退款/争议窗口（最小化）

### 8.3 必需系统能力︱Existence‑Required Capabilities
- 邀请制与私密分享：生成不可预测的邀请 token，支持链接、二维码与分享卡片；链接可配置过期时间。  
- 用户创建 market（最小闭环）：提供受限输入字段与校验（标题、选项、结算时间、最小 stake、手续费），默认私密发布；可配置为“需审核后可结算/可传播”的最小策略；Admin 具备下架/冻结/拒绝结算的最小处置能力。（v2）  
- 实时聊天：对战页内的文本聊天能力（仅对参战双方/受邀群体可见），支持消息发送、基础频率限制、消息持久化与审计；不引入基于聊天的自动化判定或推荐。（v2）  
- USDC 入池与结算闭环：  
  - 入池约束：最小入池额（Min Stake）、池子关闭时间（Close Time）、平台手续费（Fee%）。  
  - 结算逻辑：关闭后锁定参与；由 Admin/预设规则触发结算；派奖按「(总池 - 手续费) * (个人赢家 stake / 总赢家 stake)」分配；失败可退款。  
- 状态机与审计：对决状态（draft/pending/open/closed/resolving/resolved/cancelled/refunded），每次资金与状态变更写入审计日志。  
- 反滥用最小措施：创建频率限制、邀请 token 防枚举、基础风控（异常失败率告警）。  
- 指标采集最小集：邀请打开数、连接钱包数、入池数、对决创建数、结算成功率、手续费收入、退款率。

### 8.4 技术框架选型︱Engineering Baseline
- 前端 Frontend：Next.js + React + Zustand + TanStack Query + Zod + Tailwind  
- 后端 Backend／API：Next.js Route Handlers（或独立 Node API）+ 钱包/签名校验 + USDC 结算/转账服务（Backend Transfer USDC）  
- 数据库 Database：PostgreSQL + Drizzle ORM + drizzle-kit（migration）  
- 云部署 Cloud Deploy：Vercel（Web/API）+ 托管 PostgreSQL（Neon/Supabase/RDS 其一）+ 任务/队列（用于结算与对账的最小后台作业）
